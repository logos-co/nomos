## Findings by bug class

### Contradicts spec

#### 20261008T090517-4445d0/1 — IBD retries failed block downloads forever instead of failing so the node can terminate; it also refuses to complete while any one peer's tip stays unsyncable

**Status:** confirmed (first pass claude, second pass codex independently reran the proof and re-read the code) · **Severity:** medium · **Confidence:** high · **Class:** contradicts-spec

**Locations:** `services/chain/chain-network/src/bootstrap/ibd.rs:174-187`, `services/chain/chain-network/src/bootstrap/ibd.rs:231-253`

**Claim.** The spec's Initial Block Download says: "If none of download succeeds (e.g. network errors or invalid blocks), IBD is considered failed" (the reference code raises IBDFailure when `num_success == 0`, i.e. success with ≥ 1 peer completes IBD), and "If the node fails to catch up with at least one IBD peer (e.g., network error or invalid blocks), the node is terminated with an error, allowing the operator to restart the node with other IBD peers." The implementation only returns an error (`AllPeersFailed`) when no configured peer returns a *tip*. Block-download failures — the spec's own examples, network errors and invalid blocks — never fail IBD: `download_blocks` loops `collect_unsynced_tips -> enqueue -> drain -> sleep(round_delay)` until every fetched tip is in the local tree, so a peer whose tip can never be downloaded or applied makes the loop spin forever. The node never terminates with an error, never notifies IbdCompleted, never starts the Prolonged Bootstrap timer, never listens for new blocks and never proposes. Conversely, when one of several peers succeeds, the spec completes IBD (`num_success >= 1`) while the implementation still blocks on the failing peer's tip.

**Repro (test, fails on 0.3.0):**
```
cargo test --locked -p logos-blockchain-chain-network-service --all-features finding_20261008t090517_4445d0_1
```
Artifact: `services/chain/chain-network/src/finding_20261008t090517_4445d0_1.rs` on the proof branch. A single configured peer answers GetTip with an unseen tip but every block request fails with a network error; the test gives `run()` 15 seconds (hundreds of rounds at 50 ms round_delay) to return anything and times out. Exit 101: "spec violation: IBD must terminate with an error when it cannot catch up with any configured IBD peer (every block download fails); it loops forever instead: Elapsed(())". The second pass independently reran it with the same result.

**Evidence.** `ibd.rs:174-187`: the only exits from the round loop are `unsynced_tips.is_empty()` (success) and the `?` on `collect_unsynced_tips`, which errors only when *no* peer returned a tip across all retry attempts (`ibd.rs:231-253`, fetch_tips_with_retry/AllPeersFailed). A failed download merely logs and cancels (`drain_downloader`, `ibd.rs:206-224`) and the round repeats. The crate's own doc comment confirms the narrowing: "Returns ... Error::AllPeersFailed if no IBD peer returned a tip" (`ibd.rs:126-128`), and the test `block_apply_error_triggers_cancel` (`ibd.rs:510-515`) documents "The IBD then keeps retrying that same tip (no per-tip retry limit yet)". `chain-network/src/lib.rs:339-356` (traced, outside unit) shows graceful shutdown is wired only to this Err path, so the spec's termination never happens for download failures.

**Impact.** Deterministic whenever any configured IBD peer serves a tip whose chain cannot be downloaded or applied; the node hangs in IBD indefinitely with no terminating error for the operator.

**Fix hint.** Track per-peer download success in the IBD loop: bound retries for a tip (or a round count/deadline), count a peer as failed when its tip repeatedly cannot be downloaded or applied, finish IBD once every peer is either caught up or failed with at least one success (spec: `num_success >= 1`), and return an IBD-failure error when no peer could be caught up so chain-network's existing shutdown path (`lib.rs:339-356`) fires. The supplied test fails without this and passes with it.

#### 20261008T090517-4445d0/7 — Hybrid block responses append the immutable block twice at the storage-to-engine boundary, violating parent-to-child order

**Status:** confirmed (raised by the second pass, codex; adjudicated by claude in this merge pass — repro rerun and code re-read) · **Severity:** low · **Confidence:** medium · **Class:** contradicts-spec

**Locations:** `services/chain/chain-service/src/sync/block_provider.rs:412-434`, `services/chain/chain-service/src/sync/block_provider.rs:364-375`

**Claim.** The Downloading Blocks section requires the responder to return blocks in parent-to-child order and start from the highest common ancestor. When a known starting block is below the responder's LIB and the target is above it, `compute_path_from_storage_and_engine` scans immutable blocks inclusively through the LIB, then appends an engine path that also includes the LIB. `stream_blocks_from_path` only skips the first starting block, leaving the LIB twice consecutively in the streamed response. The second LIB is not a child of the first LIB. This contradicts the required response ordering and wastes an entry of the limited batch. Current IBD explicitly tolerates AlreadyApplied, so this finding does not claim a demonstrated consensus failure or node shutdown.

**Repro (test, fails on 0.3.0):**
```
python3 services/chain/chain-service/tests/finding_20261008t090517_4445d0_7/runner.py
```
Artifact: `services/chain/chain-service/tests/finding_20261008t090517_4445d0_7/runner.py` (plus `proof.rs`) on the proof branch. The runner compiles the unchanged provider source with the injected test as a temporary integration target (removed in a `finally`), edits no audited source or manifest. The test stores a parent-linked immutable prefix at slots 1..5, builds the engine from that slot-5 LIB, adds three non-immutable descendants at slots 6..8, and requests slot 8 with only slot 1 known. Expected stream slots `[2,3,4,5,6,7,8]`; actual `[2,3,4,5,5,6,7,8]`. The merge pass reran it: exit 101, the slot-5 HeaderId `f640add4…` appearing twice consecutively.

**Evidence.** Independently traced in this merge pass: `compute_path_from_storage_and_engine` (`block_provider.rs:404-437`) scans `start_block_slot..=target_block_slot`, so the immutable scan's last entry is the stored LIB; `compute_path_from_engine` (`:364-401`) is then called with `start_block = cryptarchia.lib()` and push_fronts every block down to and including that same LIB; `storage_path.extend(engine_path)` at line 434 concatenates both copies. `stream_blocks_from_path` (`:165-189`) only does `skip(1)` for the requester's known start block, so the mid-path duplicate is streamed.

**Impact.** Deterministic when the starting known block is below LIB, the target is above LIB, and the batch has room to cross from storage into the engine. Affects response ordering conformance and batch efficiency; this repo's IBD tolerates the duplicate, but stricter third-party requesters may not.

**Fix hint.** Join the paths without duplicating their common LIB endpoint, and account for that overlap when assigning the remaining batch limit; retain one skip for the requester's known starting block. The supplied regression asserts a hybrid response contains slots `[2,3,4,5,6,7,8]`; also cover batch limits that end at or just beyond the LIB.

### Missing requirement

#### 20261008T090517-4445d0/2 — Bootstrapping from a checkpoint is unimplemented: no checkpoint import flow, no checkpoint-triggered Bootstrap rule, no checkpoint provider API

**Status:** confirmed (second pass independently inspected the code paths) · **Severity:** medium · **Confidence:** medium · **Class:** missing-requirement · **Prose-only:** no runnable test can demonstrate a wholly absent capability; evidenced by inspection and grep.

**Location:** `services/chain/chain-service/src/bootstrap/state.rs:17-27`

**Claim.** The spec defines bootstrapping "From the checkpoint block obtained from a trusted checkpoint provider" as one of its three covered cases, requires the Bootstrap fork choice rule when "a node is starting with B_imm set to the Genesis block or from a checkpoint block", specifies importing the downloaded checkpoint block and ledger state as B_imm and c_loc before IBD, termination with an error when no peer's chain connects to the checkpoint, and a trusted-provider HTTP API (GET /checkpoint). None of this exists as a checkpoint flow: `choose_engine_state` only tests `lib_id == genesis_id || config.force_bootstrap` and carries a TODO deferring checkpoints to issue #1454. The generic `StartingState::Lib` (`states.rs:94-99`) can seed a supplied LIB and ledger — some building blocks exist — but there is no checkpoint discriminator: a fresh non-genesis LIB without a persisted engine state selects the Online rule unless the operator also sets force_bootstrap, violating "the Bootstrap fork choice rule must be used upon startup". No checkpoint download, provider endpoint, or client exists anywhere in the chain services.

**Repro (command):** `grep -rni checkpoint services/chain consensus/cryptarchia-sync services/network` — the only hit is the TODO at `state.rs:26`.

**Evidence.** `state.rs:17-27`: the Bootstrap conditions are genesis-LIB, force_bootstrap, and the offline grace period; lines 25-26 read `// TODO: Implement other criteria for bootstrapping — Checkpoint: …/issues/1454`. The second pass independently read `StartingState` in `chain-service/src/lib.rs:600-609`, `states.rs:84-118`, and `bootstrap/state.rs:17-27` and reran the grep, confirming the absence of any checkpoint discriminator, automatic Bootstrap selection for checkpoint starts, and the provider HTTP flow.

**Impact.** Always: the capability is absent. Affects the spec sections 'Bootstrapping from Checkpoint', 'Checkpoint Provider HTTP API', and the checkpoint clause of 'Setting the Fork Choice Rule'. Genesis and local-tree bootstrapping are unaffected. Trace rows 5, 34, 35 and 36 all fold into this finding.

**Fix hint.** Implement the checkpoint flow per the spec: a client for GET /checkpoint (multipart: checkpoint_block, checkpoint_ledger_state), an import step that sets the checkpoint as B_imm and c_loc, a `StartingState::Checkpoint` (or a flag on `StartingState::Lib`) that `choose_engine_state` maps to `State::Bootstrapping` unconditionally, and error termination when no IBD peer's chain connects to the checkpoint. First failing test: construct `choose_engine_state` with a checkpoint-derived starting state and no force_bootstrap, assert Bootstrapping.

### Wrong default

#### 20261008T090517-4445d0/4 — Default Prolonged Bootstrap Period is 1 hour; the spec constant T_boot is 24 hours

**Status:** confirmed (second pass independently read the default and traced the timer path) · **Severity:** medium · **Confidence:** medium · **Class:** wrong-default · **Prose-only:** evidenced by command output and code tracing; building the node binary crate exceeds this container, so no failing test is supplied.

**Locations:** `services/chain/chain-service/src/bootstrap/config.rs:8-14`, `nodes/node/binary/src/config/cryptarchia/serde/service.rs:46-54`

**Claim.** The spec's constants table sets T_boot to 24 hours and repeats "This protocol configures the Bootstrap Period to 24 hours." The unit's `BootstrapConfig` leaves `prolonged_bootstrap_period` as a free config value with no default encoding the constant, and the only default the codebase supplies — the operator-facing serde default in the node binary — is `Duration::from_hours(1)`. A node run with default configuration switches from Bootstrap to Online (and starts proposing) 23 hours earlier than the spec mandates, shrinking the window the 24-hour period exists for (comparing the synced chain against a broader peer set; long-range/isolated-network mitigation).

**Repro (command):** `grep -n -A 8 "impl Default for BootstrapConfig" nodes/node/binary/src/config/cryptarchia/serde/service.rs` — shows `prolonged_bootstrap_period: Duration::from_hours(1)`.

**Evidence.** `config.rs:8-14` declares the field with serde bounds but no default (contrast `offline_grace_period`, whose 20-minute default matches the spec's T_offline at `config.rs:29-31`). `service.rs:46-54` supplies the 1-hour default, with `#[serde(default)]` on the struct (line 38), so an omitted bootstrap section silently gets a 1-hour PBP. The second pass independently read `service.rs:6-12` and `37-54` (both enclosing Config and BootstrapConfig use serde(default)) and traced `chain-service/src/lib.rs:787-799` to `service/phases/pbp.rs:82`, which actually sleeps for the supplied period and then switches online — the effective default really is 23 hours short.

**Impact.** Every node whose YAML omits `prolonged_bootstrap_period`; deterministic. Explicitly configured deployments are unaffected by the default but equally diverge from the constant.

**Fix hint.** Set the default to `Duration::from_hours(24)` in `service.rs` (and/or give the unit's `BootstrapConfig` a serde default of 24 h mirroring `offline_grace_period`). Failing test: deserialize an empty bootstrap config section and assert `prolonged_bootstrap_period == Duration::from_hours(24)`.

### Spec drift

#### 20261008T090517-4445d0/3 — Sync protocol ID is fork-digest-derived (`/logos-blockchain/<fork>/chainsync`), not the spec's `/logos-blockchain/cryptarchia/sync/1.0.0`

**Status:** confirmed (second pass traced the full wiring from derivation to the libp2p behaviour) · **Severity:** low · **Confidence:** medium · **Class:** spec-drift · **Prose-only:** the likely fix target is the LIP text, so no failing code test is supplied.

**Locations:** `nodes/node/binary/src/config/deployment/protocols.rs:52-72`, `consensus/cryptarchia-sync/src/libp2p/behaviour.rs:160-165`

**Claim.** The spec fixes the libp2p protocol IDs: `/logos-blockchain/cryptarchia/sync/1.0.0` (mainnet) and `/logos-blockchain-testnet/cryptarchia/sync/1.0.0` (testnet). The implementation instead derives the chain-sync protocol name from the deployment's fork digest: `/logos-blockchain/<fork digest in hex>/chainsync`, with no version segment and no testnet namespace variant; the spec string appears nowhere in the repository. The drift looks deliberate — the derivation module documents that fork-scoped names keep nodes on different forks from talking — so the fix is likely to the LIP, but as published the spec and the wire are incompatible: these strings fail libp2p protocol negotiation, so an implementation following the LIP cannot open a sync stream to this node.

**Repro (command):** `grep -rn "cryptarchia/sync" --include='*.rs' --include='*.yaml' --include='*.toml' .` — no matches (exit 1): the spec's ID is absent from the repo.

**Evidence.** `behaviour.rs:160` takes the protocol name as a parameter; the production value comes from `protocols.rs:52` (`chain_sync: stream_protocol(&fork, "chainsync")`) and `:65-72`, yielding `/logos-blockchain/<64-hex-fork-digest>/chainsync` (asserted by the test at `protocols.rs:92-95`). The module doc (`protocols.rs:1-8`) explains the fork-isolation intent. The second pass independently traced `ProtocolNames::derive` at `protocols.rs:44-72`, `network/mod.rs:34` passing `protocol_names.chain_sync` to the backend, and `behaviour.rs:160-180,190-228` accepting/opening that supplied protocol — confirmation by code tracing, not absence-only grep.

**Impact.** Always: every sync stream uses the derived name. Wire-level interoperability with any third-party LIP-conformant implementation; no effect between nodes built from this repo.

**Fix hint.** Resolve in the LIP: replace the fixed mainnet/testnet protocol IDs with the fork-digest derivation rule (`NAMESPACE/<fork-digest-hex>/chainsync`) and its rationale — or, if the fixed IDs are normative, change `ProtocolNames::derive` to emit them. A code-side test would assert the derived name equals the LIP string and currently fails.

#### 20261008T090517-4445d0/6 — Restart within the grace period resumes the persisted Bootstrapping state; the spec's 'otherwise Online' wording doesn't cover restarts mid-bootstrap

**Status:** unconfirmed (second pass verdict: unclear — the code behaviour is established, but whether the spec normatively forbids it is ambiguous) · **Severity:** info · **Confidence:** medium · **Class:** spec-drift · **Prose-only:** no failing test supplied; the code, not the spec, appears correct, and a test would pin the stale spec letter.

**Locations:** `services/chain/chain-service/src/bootstrap/state.rs:40-42`, `services/chain/chain-service/src/states.rs:67-70`

**Claim.** Per 'Setting the Fork Choice Rule', a node uses Bootstrap only in three cases (genesis/checkpoint LIB, certain offline > T_offline, operator flag) and "Otherwise, the node uses the Online fork choice rule." A node restarted mid-bootstrap within the grace period matches none of the three, so the spec's letter says Online. The implementation instead resumes the last persisted engine state: `check_offline_grace_period` returns `last_state.state` when `elapsed <= grace_period`, so a node that was Bootstrapping (e.g. inside the PBP) and restarts within 20 minutes comes back Bootstrapping. The code is the safer, more coherent behaviour — dropping to Online on a quick restart would cut the PBP short, contradicting "a node must maintain the Bootstrap fork choice rule during the Bootstrap Period" — so the stale document is the likely fix target. The second pass holds that the spec's clauses do not unambiguously specify mid-bootstrap recovery at all, leaving the alleged divergence unclear rather than established.
