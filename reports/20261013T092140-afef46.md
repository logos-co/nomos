- **Proven violations** (the code does something the specification forbids, demonstrated by a failing test): finding 1 — the selector polarity divergence is demonstrated by a proof test both passes ran and saw fail. - **Documentation and attestation drift** (the repository's own conformance record contradicts the code or itself): finding 1, as above — the LIP text and the shipped convention disagree.
- **Unavailable external evidence** (a static checkout cannot see release attachments, external submissions or third-party reports; absence is not asserted as non-existence): no finding is filed unconfirmed, but the constraints enforced only inside the prebuilt circuit (`lbc-pol-sys`) are external evidence throughout — trace rows 2, 11, 14 and 17 — and the circuit's agreement with the Rust side rests on the end-to-end prove+verify tests, not on circuit source inspection.

### Spec-drift (proven violation of the document's letter / documentation drift)

#### Finding 1 — PoL Merkle witness selectors invert the LIP's left (0) / right (1) encoding — **confirmed**, medium severity, high confidence

The LIP ("Circuit Private Inputs", item 2) defines the membership witness as the complementary Merkle nodes plus boolean selectors "indicating whether they are left (0) or right (1)". The implementation does the opposite: `merkle_path_to_witness` sets a selector to `true` exactly when the complementary node is `MerkleNode::Left`, and `lb-pol` serializes `true` as field element 1 — so a LEFT complementary node is encoded as 1 where the spec says 0. The code also emits selectors in root-to-leaf order while the path nodes stay leaf-to-root; the LIP does not prescribe array ordering, so both passes treat the reversal as observed context, not an independent violation. The shipped prebuilt circuit (`lbc-pol-sys`) accepts these witnesses — the end-to-end prove+verify tests pass — so the deployed convention is the inverted one and the LIP text is stale relative to it. What the finding does not establish: no soundness bug or fund loss in the shipped code (prover, circuit and verifier are self-consistent); the circuit's internal reading is inferred from the end-to-end tests, not from circuit source, which is external evidence. The practical harm is interoperability: an independent prover written from the LIP as published would emit bit-flipped selectors, compute wrong Merkle roots in-circuit, and fail to produce valid proofs of leadership.

- Locations: `core/src/proofs/merkle.rs:13-19` (selector computed as `matches!(path[31-i], MerkleNode::Left(_))` — true for a LEFT sibling, reverse-indexed), `core/src/proofs/leader_proof.rs:321-322` (`LeaderPrivate::new` feeds both witness pairs to the circuit inputs), `zk/proofs/pol/src/wallet_inputs.rs:101-105` (`true → Fr::ONE`, `false → Fr::ZERO`).
- Repro: `cargo test --locked -p logos-blockchain-core --test pol_spec_selector_encoding_finding_1` → observed: "assertion `left == right` failed: spec says selectors mark complementary nodes as left (0) or right (1); the path has 31 right complementary nodes so 31 selectors must be 1, but the witness sets 1 (the code emits 1 for LEFT siblings)  left: 1  right: 31 … test result: FAILED. 0 passed; 1 failed".
- Second pass: confirmed — independently re-ran the proof test (exit 101, failing at `core/tests/pol_spec_selector_encoding_finding_1.rs:78`, actual 1 vs expected 31), independently read the LIP sentence and the full code path from `DynamicMerkleTree::path` through `merkle_path_to_witness`, `LeaderPrivate::new` and `wallet_inputs.rs`. It limited the confirmation to the polarity divergence (ordering is unspecified by the LIP) and noted the circuit interpretation and alternative-prover impact need external circuit evidence. Its broader sweep (public-input ordering, little-endian key halves, ticket domain/argument order, strict comparison, threshold arithmetic, root validation, epoch snapshot selection, fresh leader key generation; four additional tests run green) found no further divergence.
- Fix: decide which side is authoritative. Most likely the LIP is stale: amend "Circuit Private Inputs" item 2 to state the deployed polarity (complementary node on the left = 1, equivalently "current node is the right child") and the ordering of both arrays. If instead the LIP is authoritative, invert the polarity in `merkle_path_to_witness` and align the circuit, regenerating `lbc-pol-sys`. The proof test `core/tests/pol_spec_selector_encoding_finding_1.rs` states the spec sentence, fails on the current code, and passes once code and document agree on left = 0 / right = 1. (The brief's acceptance asks confirmed code findings to carry a failing test in one of the unit's crates — this test, in `logos-blockchain-core`, is it; the recommended resolution is nonetheless a document correction, making this in substance a prose fix once the LIP is amended.)

No findings were raised in the contradicts-spec, wrong-default, off-by-requirement, missing-requirement or undefined-behaviour classes.
