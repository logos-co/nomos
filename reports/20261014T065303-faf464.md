### Contradicts-spec (proven violation; documentation drift)

#### Finding 3 (handle stamped by the harness on merge) — TSI observation period follows configurable nonce phases instead of the specified six base periods — **confirmed**, medium severity, medium confidence, raised by second pass, adjudicated by merge pass

The specification fixes `PERIOD = 6 * floor(k/f)` and calls `density_over_slots(epoch_slot, PERIOD)`. `Config::total_stake_inference_period` instead returns `nonce_contribution_period` — `base_period_length * (nonce_buffer + stake_stabilization)` — and `BlockDensity` derives its observation window from that phase-dependent period. The two coincide only when the snapshot and buffer phases happen to sum to six base periods, as in the standard 3/3/4 split. Under an accepted 1/1/8 split (k=5, f=1/2: epoch still 100 slots), the code observes [0,20) where the spec requires [0,60): blocks in the remaining four base periods are ignored, yielding a different next-epoch estimate and different derived lottery constants. The finding establishes a consensus-state divergence under nonstandard-but-accepted configurations only; it shows no fund loss and does not affect deployments on the standard 3/3/4 split.

- Locations: `ledger/src/config.rs:104-106` (`total_stake_inference_period` returns `nonce_contribution_period`), `ledger/src/config.rs:81-90` (the phase-dependent product), `ledger/src/cryptarchia/block_density.rs:29-35` (window derived from that period).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test finding_20261014t065303_faf464_3` → observed: `observation_period_must_be_six_base_periods ... FAILED` — ``assertion `left == right` failed: PERIOD = 6*floor(k/f), independent of configurable nonce phases — left: 1, right: 1000``. Thirty headers at slots 30..59 lie inside the spec's window (measured density 30 = expected 30, estimate 1000 retained) but outside the code's (density 0, estimate clamps to 1).
- Second pass: raised the finding; ran the same command and recorded the identical failure (left 1, right 1000), after tracing config.rs:81-90,104-106 into `BlockDensity::compute_period_range` and `LedgerState::from_utxos`/`update_epoch_state`.
- Merge-pass adjudication: re-ran the exact repro from the proof branch and reproduced the identical assertion failure at `finding_20261014t065303_faf464_3.rs:155`; independently read config.rs:81-90, config.rs:104-106 and block_density.rs:29-35 and confirmed the window arithmetic ([0,19] observed vs [0,59] required under the 1/1/8 split); read the proof test in full and verified its `AlwaysValidProof` bypasses only ZK leadership verification, not the density counting and inference under test. Confirmed.
- Fix: derive the TSI period as six base periods (`6 * base_period_length`) independently of the nonce phases and anchor the window at the epoch's first slot — or reject phase configurations whose snapshot-plus-buffer length is not six base periods before constructing consensus state. The committed test `ledger/src/cryptarchia/test/finding_20261014t065303_faf464_3.rs` (loaded via `ledger/tests/finding_20261014t065303_faf464_3.rs`) fails on 0.3.0 and passes with either fix.

#### Finding 2 `F-4cfdb5a8` — Unit-test comment states total stake 'should decrease' on high block density, inverting the spec's direction — **confirmed**, info severity, high confidence

The spec's overview reads "a higher fraction of occupied slots implies more stake participating in consensus", so measured density above expected must raise the estimate. The comment at `stake.rs:114` — "total stake should decrease because blocks more than expected were produced" — states the opposite, while the code and the test's own assertion (`result > total_stake_estimate`, stake.rs:115-118) implement the spec correctly. **Prose-only finding:** only the comment is wrong; there is no runtime divergence, so no behavioural test can fail on it — but the false claim about the controller's sign could mislead a maintainer into "fixing" the assertion the wrong way.

- Locations: `ledger/src/cryptarchia/stake.rs:114` (the inverted comment), `ledger/src/cryptarchia/stake.rs:115-118` (the correct assertion), `ledger/src/cryptarchia/stake.rs:42-51` (the correct sign in the controller).
- Repro: `grep -n -A 4 "total stake should decrease" ledger/src/cryptarchia/stake.rs` → observed: line 114's comment followed by the assertion `result > total_stake_estimate` (exit zero shows the contradiction in place).
- Second pass: confirmed — independently read stake.rs:104-118 and re-derived the sign from the executed arithmetic at lines 42-51 (measured > expected makes the density difference negative; subtracting the negative correction increases the estimate), resting on its own read rather than the first-pass prose.
- Fix: change the comment to the spec's direction, e.g. `// total stake should increase because more blocks than expected were produced (higher occupancy implies more participating stake)`. Docs-only change; no test can enforce it.

### Undefined-behaviour (proven runtime behaviour; spec status unsettled)

#### Finding 1 `F-12eadf12` — total_stake_inference panics instead of returning a clamped estimate when the corrected total stake exceeds u64::MAX — **unconfirmed**, medium severity, medium confidence

The spec's pseudocode ends with `max(new_total_stake_estimate, 1) as u64` — a lower clamp and a cast, suggesting a total function over u64 estimates. The implementation (`StakeInference::total_stake_inference`, stake.rs:66-69) computes the update in i128 and converts with `try_into().expect("After precision it should fit in a u64")`, which panics whenever the corrected estimate exceeds `u64::MAX` — e.g. with f = 1/2, a fully occupied window doubles the estimate, so any estimate above `u64::MAX/2` aborts. The panic fires inside `update_epoch_state` while applying the first block of a new epoch, so every node following that chain crashes deterministically at the same block — a chain halt, not a single-node fault. What the finding does **not** establish: that the spec is violated. The spec writes the intermediate `tse_p` as a u64 product that the repro's input already overflows, and names no valid-input bound, overflow rule or upper clamp — the above-u64 case is undefined in the staged text, which is why both passes leave the finding unconfirmed rather than confirmed or disputed.

- Locations: `ledger/src/cryptarchia/stake.rs:66-69` (the panicking conversion), `ledger/src/cryptarchia/mod.rs:304-307` (called during block application at the epoch transition).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test finding_20261014t065303_faf464_1` → observed: `panicked at ledger/src/cryptarchia/stake.rs:69:14: After precision it should fit in a u64: TryFromIntError(PosOverflow)` (genesis note of u64::MAX stake, 32 blocks in a 30-expected-density window, transition at slot 100).
- Second pass: unclear — independently ran the exact repro and reproduced the panic at stake.rs:69, and independently read stake.rs:36-51,66-69 and mod.rs:304-307; but held that the spec supplies no upper-range handling or totality guarantee for every u64 input, so the panic is real while its status as a spec divergence is unresolved. It also verified the audited ref: tag object `1da2d9d6…` peels to `f76be2dd…`, which the audited files match.
- Disposition: both passes agree on every fact — the panic, its location, its deterministic consensus-wide reach, and that the adjacent unit test `test_total_stake_inference_very_high_stake` (stake.rs:154-169) only exercises the shrinking direction. In dispute is only whether the spec's closing `max(…, 1) as u64` promises totality over inputs its own u64 intermediates could not represent; absent an explicit valid-input bound in the spec, the finding stays unconfirmed. Trigger likelihood is configuration-dependent: it needs estimate × (measured/expected) > ~1.8e19, so deployments whose total supply stays below ~`u64::MAX * f` are safe in the honest case.
- Fix: clamp the conversion — `u64::try_from(new_total_stake_estimate.max(1)).unwrap_or(u64::MAX)` (or clamp to the lottery's maximum supported stake) — mirroring the existing lower clamp; or have the spec state an explicit valid-input bound. The committed test `ledger/tests/finding_20261014t065303_faf464_1.rs` fails on 0.3.0 (panic at stake.rs:69) and passes once the update returns a clamped estimate.
