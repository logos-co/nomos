### contradicts-spec (proven violation)

#### Finding 3 (F-4c00393e) — Observation period follows configurable epoch phases instead of the specified 6⌊k/f⌋ — **confirmed**, medium severity, high confidence, raised by second pass, adjudicated by merge pass

The LIP fixes the observation period at `PERIOD = 6⌊k/f⌋` and measures density over `[epoch_slot, epoch_slot + PERIOD)`. The implementation instead derives the period from the configurable epoch phase schedule: `Config::total_stake_inference_period()` returns `nonce_contribution_period()`, which is `base_period_length × (epoch_period_nonce_buffer + epoch_stake_distribution_stabilization)`. Those two public phase multipliers are nowhere constrained to sum to six, so any accepted configuration with a different split silently uses the wrong period — with k=1, f=0.1 and phases 2/3/4 the code measures over 50 slots instead of the required 60. Both the measured window (`BlockDensity` closes its range early) and the expected-density denominator (`expected_density_p = PERIOD × f_p`) shift together, so the inferred stake and the subsequent leadership lottery constants diverge from the specified values. What the finding does not establish: no divergence on the standard 3/3/4 split that every shipped deployment uses, and no fund loss is shown — the scope is configurations whose phase sum differs from six.

- Locations: `ledger/src/config.rs:104-105` (`total_stake_inference_period` delegates to `nonce_contribution_period`), `ledger/src/config.rs:81-90` (phase-derived product), `ledger/src/cryptarchia/block_density.rs:31-36` (range from phase-anchored snapshot minus that period), `ledger/src/cryptarchia/mod.rs:754-757` (period fed to the inference).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test e08b60_3` → observed: `assertion left == right failed: LIP PERIOD = 6 floor(k/f) must remain 60 when k=1 and f=0.1; epoch phases are not in the formula — left: 50, right: 60`.
- Second pass: raised the finding, with its own run of the same test (failed, left 50 / right 60) and an independent trace of config.rs, block_density.rs and stake.rs; it noted the first pass had recorded this as a remark under R4 rather than a finding.
- Merge-pass adjudication: re-ran the repro from the proof branch — one test collected, failed exactly as recorded (left: 50, right: 60; the standard-phase assertion passed first) — and independently read config.rs:81-90, 104-106 and block_density.rs:29-35, confirming the phase multipliers replace the spec's fixed factor of six.
- Fix: derive the inference period directly as `6 × base_period_length`, independent of nonce phase durations, and construct the density range from the epoch's first slot plus this period (anchoring to the phase-derived snapshot would otherwise shift the observation start); alternatively reject epoch schedules whose phases do not implement the specified range. The proof test `test/20261014T074144-e08b60/3/proof.rs` fails without the fix and passes with it.

#### Finding 1 (F-4cfdb5a8) — Test comment states the opposite correction direction from the spec — **confirmed**, info severity, medium confidence

The LIP implies that a higher observed slot occupancy means more participating stake, so the estimate must increase: `density_diff_p = expected − measured` goes negative, the correction goes negative, and the new estimate exceeds the old. The unit test `test_total_stake_inference_high_block_density` asserts exactly that (`result > total_stake_estimate`), but the comment directly above it — "total stake should decrease because blocks more than expected were produced" — states the opposite of the specified behaviour. The code and the assertion are correct; only the comment is wrong. This is a prose-only finding (documentation/attestation drift): no code path diverges, so no failing test exists or is possible for it, and the repro is the command whose output shows the contradiction in place.

- Locations: `ledger/src/cryptarchia/stake.rs:114` (the wrong comment), `ledger/src/cryptarchia/stake.rs:115-118` (the correct assertion it contradicts).
- Repro: `grep -n -A 5 'total stake should decrease' ledger/src/cryptarchia/stake.rs` → observed: line 114 carries the comment immediately above `assert!(result > total_stake_estimate, ...)` at lines 115-118.
- Second pass: confirmed — ran the exact repro command (exit 0), read the controller at stake.rs:43-51 and the test at 104-119, and independently derived from the spec that at twice the expected density with beta=1 the estimate doubles; concluded the comment contradicts the specified direction while the implementation and assertion satisfy it. Documentation-only.
- Fix: change the comment at `ledger/src/cryptarchia/stake.rs:114` to state the specified direction, e.g. "total stake estimate should increase because more blocks than expected were produced (more stake is participating than estimated)". No code change.

### undefined-behaviour (failing test; spec interpretation unsettled)

#### Finding 2 (F-12eadf12) — total_stake_inference panics instead of producing a u64 when the corrected estimate exceeds u64::MAX — **unconfirmed**, medium severity, medium confidence

The LIP's algorithm ends with `max(new_total_stake_estimate, 1) as u64`. The implementation widens the arithmetic to i128 (avoiding the u64 overflow latent in the spec's own pseudocode) but converts back with `try_into().expect("After precision it should fit in a u64")`, which panics whenever the corrected estimate exceeds `u64::MAX`. With beta = 1 the update multiplies the estimate by `1 + (measured − expected)/expected`, so a chain state whose estimate exceeds `u64::MAX/2` with an observation window holding at least twice the expected occupied slots panics deterministically inside `LedgerState::update_epoch_state` — every validating node crashes at the same epoch transition. The panic is proven by a failing end-to-end test through the public API. What the finding does not establish: that the spec requires a defined value at this input. The second pass's objection, which keeps the status at unconfirmed rather than confirmed: the spec's `max(.., 1)` clamps only the lower bound, Rust-style `as u64` does not saturate, and the spec's own `tse_p = total_stake_estimate * PRECISION` already overflows u64 for the proof input — so the "clamped u64 for every input" premise is an interpretation the staged text does not settle. The trigger is also configuration-dependent: it requires a token supply approaching 2^63 base units.

- Locations: `ledger/src/cryptarchia/stake.rs:66-70` (the panicking conversion), `ledger/src/cryptarchia/mod.rs:304-307` (unconditional call on the consensus path; also mod.rs:371-379 for skipped epochs), `ledger/src/cryptarchia/stake.rs:158` (existing comment "maximum stake supported is half" documenting the limit without enforcing it).
- Repro: `cargo test --locked -p logos-blockchain-ledger --all-features --test e08b60_2` → observed: `test epoch_transition_clamps_total_stake_estimate_instead_of_panicking ... FAILED — panicked at ledger/src/cryptarchia/stake.rs:69:14: After precision it should fit in a u64: TryFromIntError(PosOverflow)`.
- Second pass: unclear — ran the repro (one test collected, failed with exactly the claimed panic) and independently read stake.rs:37-51 and 66-69, so the runtime panic is agreed; but it found the asserted spec requirement of a saturated upper bound not established by the staged pseudocode, and said clarifying the LIP's valid input bounds and overflow semantics (wrap, saturate, or error) would resolve the verdict.
- Disposition: both passes agree the panic is real, deterministic, reachable through the public API, and network-wide in scope once triggered; the clause in dispute is whether `max(.., 1) as u64` defines behaviour above `u64::MAX` at all. Unconfirmed per the rules — the staged spec text cannot settle it either way — and never counted as a pass.
- Fix: clamp instead of panicking, e.g. `u64::try_from(new_total_stake_estimate.max(1)).unwrap_or(u64::MAX)` (or clamp to a protocol-defined maximum total stake before the division), and/or amend the LIP to state input bounds and overflow semantics explicitly. The proof test `ledger/tests/e08b60_2.rs` fails without the fix and passes once the result is clamped.
