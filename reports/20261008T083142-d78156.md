**Trace notes** (from the first pass):

- The spec's `for c_fork in forks` loop order is unspecified; the engine iterates `HashTrieSet` tips in arbitrary order (`lib.rs:270-272`). The sequential-tournament order sensitivity of `maxvalid-bg` is inherent to the spec's own pseudocode, so this is recorded as a note, not a finding.
- `apply_header` admits a child in the *same* slot as its parent (`lib.rs:244` rejects only `parent.slot > slot`). Slot monotonicity is governed by the parent Cryptarchia Protocol LIP (audited by another brief); within this unit that admitted state is what makes finding /1 reachable.

## Findings by bug class

### Bug class: off-by-requirement

<a name="finding-1"></a>
#### 20261008T083142-d78156/1 — maxvalid-bg density window includes the divergence point's own slot

**Status:** confirmed (first pass claude, confirmed by second pass codex) · **Severity:** low · **Confidence:** high · **Class:** off-by-requirement

**Claim.** LIP-147 defines `density(b_i, d, s_gen)` as "the number of blocks produced in the s slots *following* block `b_{i-d}`", clarified as "the number of blocks created in the *next* `s_gen` slots" after the divergence point's slot `sl_t`. The engine's bootstrap rule (`maxvalid_bg`) instead measures each chain's density as the chain length at the last block with `slot <= lca.slot + s_gen` (`walk_back_before`), which counts every post-LCA block with `slot >= lca.slot` — including a block created at slot `sl_t` itself. Such a block is admissible in the engine's state space: `apply_header` rejects a child only when `parent.slot > slot`, so a fork's first block may share the LCA's slot. A long-range fork carrying one block at the LCA's own slot therefore gets one unit of density credit the spec denies it, and can win the bootstrap fork choice against a first-seen chain of equal spec-density, weakening exactly the tie-break the Genesis rule relies on against long-range attacks.

**Locations.**
- `consensus/cryptarchia-engine/src/lib.rs:106-111` (density scoring)
- `consensus/cryptarchia-engine/src/lib.rs:316-325` (`walk_back_before`)
- `consensus/cryptarchia-engine/src/lib.rs:244-246` (`apply_header` admits equal slots)

**Repro.** Test `consensus/cryptarchia-engine/tests/finding_d78156_1.rs` on the proof branch:
```
cargo test --locked -p logos-blockchain-cryptarchia-engine --all-features --test finding_d78156_1
```
Fails on 0.3.0.

**Evidence.** (1) `lib.rs:106` computes `density_slot = lca.slot + s_gen`. (2) `lib.rs:107-108` score each chain as `branches.walk_back_before(tip, density_slot).length`; `walk_back_before` returns the newest ancestor with `slot <= density_slot`, so `.length` counts all chain blocks with slot in `[lca.slot, lca.slot + s_gen]`, not `(lca.slot, lca.slot + s_gen]` as the spec's "following"/"next `s_gen` slots" wording requires. (3) `apply_header` admits a child whose slot equals its parent's. Proof test (k=2, f=1/10, s_gen=5, LCA=genesis at slot 0): first-seen chain A has 3 blocks in the window slots 1..=3 plus 3 blocks beyond it (divergence depth 6 > k); fork B has one block at slot 0 plus 3 blocks in slots 1..=3. Spec densities are 3 vs 3 — a tie, and the strict `<` of maxvalid-bg keeps first-seen A. The engine computes 3 vs 4 and reorgs to B. The test fails with `left: 104, right: 6` (tip became fork block 104 instead of staying at A's tip 6); both passes ran it independently and saw the same failure. All 26 pre-existing package tests pass. Caveat on practical reach: header validation outside this unit (ledger/protocol LIP) likely enforces strictly increasing slots, which would make the state unreachable end-to-end; within the unit's own admitted behaviour the divergence is deterministic.

**Fix hint.** Count density as the number of blocks strictly after the LCA's slot — e.g. compute the window-end block via `walk_back_before` as today, then count only ancestors newer than `lca.slot` — for both `cmax` and the candidate. Alternatively enforce strictly increasing slots in `apply_header`, though that is governed by the parent protocol LIP. The committed test fails without the fix and passes with it.

<a name="finding-3"></a>
#### 20261008T083142-d78156/3 — floating-point rounding shortens s_gen by one slot

**Status:** confirmed (second pass codex, adjudicated and reproduced by merge pass claude) · **Severity:** medium · **Confidence:** medium · **Class:** off-by-requirement

**Claim.** LIP-147 defines `s_gen = floor(k/(4f))` over exact rationals, and density includes the block at slot `LCA.slot + s_gen`. `Config::s_gen` converts the rational active slot coefficient to `f64` before dividing, so the quotient carries binary rounding error before the floor. For k=12 and f=1/75 the mathematical value is exactly 225, but `f64(1/75)` rounds up to `0.013333333333333334`, the quotient becomes `224.99999999999997`, and the implementation floors it to 224. `maxvalid_bg` therefore excludes blocks in the specified final slot of the density window: a first-seen chain with one block in the window and divergence depth 13 remains selected over a fork with two blocks in the window (one exactly at slot 225), contradicting the spec's strict density comparison. Unlike finding /1, every block in the proof has strictly increasing slots, so this divergence does not depend on the equal-slot admissibility caveat.

**Locations.**
- `consensus/cryptarchia-engine/src/config.rs:107-113` (`s_gen` computed in `f64`; `utils/src/math.rs:252-254` shows `as_f64 = num as f64 / den as f64`)
- `consensus/cryptarchia-engine/src/lib.rs:106-110` (density window bounded at `lca.slot + s_gen`)

**Repro.** On the proof branch:
```
bash test/20261008T083142-d78156/3/run.sh
```
The runner copies `test/20261008T083142-d78156/3/proof.rs` to `consensus/cryptarchia-engine/tests/finding_d78156_3.rs`, runs it, and removes it on exit; it fails on 0.3.0 (exit 101) without editing existing unit files.

**Evidence.** Second pass ran the runner and saw both tests fail: `s_gen_uses_the_exact_specification_floor` returned 224 where 225 is expected, and `density_includes_the_exact_window_endpoint` retained tip 13 where the spec-denser fork tip 102 must win. The merge pass independently re-ran the same runner on the proof branch and saw both failures identically (`left: 224 / right: 225`; `left: 13 / right: 102`), read the `f64` division path in `config.rs:109` and `utils/src/math.rs:252-254`, and independently confirmed the arithmetic outside Rust: in IEEE-754 double precision `1/75 = 0.013333333333333334` and `12/(4·that) = 224.99999999999997`, floor 224. The density test drives the public engine: k=12, f=1/75; genesis at slot 0; local blocks at slot 1 and slots 302..313 (depth 13 > k); fork blocks at slots 2 and 225. Spec densities are 1 vs 2 (fork must win); implementation densities are 1 vs 1 and the strict comparison retains the local chain. All 26 existing library tests pass. An in-process regression test establishes the forbidden fork-choice result; no network exploit is claimed, as that would require staging peers and upstream ledger headers outside this unit.

**Fix hint.** Compute the floor with exact integer arithmetic: `(u64::from(k) * u64::from(f.denominator)) / (4 * u64::from(f.numerator))`, with an explicit policy for a zero result (see finding /2). The `u32` inputs fit these products in `u64`. Keep the regression for k=12, f=1/75 and the end-to-end density endpoint comparison; both fail on 0.3.0 and pass with the integer formula.

### Bug class: undefined-behaviour

<a name="finding-2"></a>
#### 20261008T083142-d78156/2 — Config::s_gen panics when the spec formula yields 0

**Status:** confirmed (first pass claude, confirmed by second pass codex) · **Severity:** low · **Confidence:** medium · **Class:** undefined-behaviour

**Claim.** LIP-147 defines `s_gen = floor(k/(4f))` with no lower bound: for any configuration with k < 4f (e.g. k=1, f=1/2) the formula yields 0. The spec is silent on how an implementation should treat that value. The engine picks a behaviour that matters: `Config::s_gen` computes the formula but wraps it in `NonZero::new(..).expect("s_gen with proper configuration should never be zero")`, i.e. it panics. The panic is not raised at configuration time — `Config::new` succeeds — but lazily inside `State::fork_choice`, which calls `config.s_gen()` on every fork-choice run while Bootstrapping, regardless of whether the density branch is ever taken. A node constructed with such parameters therefore crashes on the first block it receives during bootstrap. Realistic deployments use f ≤ 1/4 with k ≫ 1, so the parameter region is unlikely in practice, but nothing in the unit validates it up front and the spec's formula admits it.

**Locations.**
- `consensus/cryptarchia-engine/src/config.rs:107-113` (the panicking `expect`)
- `consensus/cryptarchia-engine/src/lib.rs:48-51` (`s_gen()` evaluated on every bootstrapping fork choice)

**Repro.** Test `consensus/cryptarchia-engine/tests/finding_d78156_2.rs` on the proof branch:
```
cargo test --locked -p logos-blockchain-cryptarchia-engine --all-features --test finding_d78156_2
```
Fails on 0.3.0.

**Evidence.** `config.rs:107-113` computes `((k as f64)/(4.0*f)).floor() as u64` and unwraps `NonZero::new` on it — `floor(1/(4·0.5)) = 0` → panic at `config.rs:112`. `lib.rs:48-51` calls `config.s_gen()` unconditionally in the Bootstrapping arm, so the panic fires on the first `receive_block`, not at setup. The proof test constructs `Config::new(k=1, f=1/2, ...)` successfully (f=1 would additionally panic earlier inside lb-pol's `LotteryConstants`, outside this unit, so f=1/2 isolates the s_gen divergence), then calls `s_gen()` under `catch_unwind` and asserts it does not panic. Both passes ran the test independently and saw the `config.rs:112` panic ("s_gen with proper configuration should never be zero") followed by the assertion failure. The second pass notes the spec's formula has a defined zero result — a zero-slot window gives density 0 to both chains and the strict `<` retains the local chain — and that no lower-bound restriction appears in the supplied spec. A Rust panic is established; whether it terminates the process depends on the caller's panic policy. Confidence held at medium: the spec does not prescribe a behaviour for s_gen=0, only admits the value; the defect is that the engine resolves the silence with a runtime abort during fork choice instead of validation or a defined degenerate rule.

**Fix hint.** Either (a) validate k ≥ 4f when the `Config` is constructed and return a `Result` so the misconfiguration is rejected before the node runs, or (b) let `s_gen` be a plain `u64` and define the degenerate window: with s_gen = 0 both densities are 0 and the strict `<` in `maxvalid_bg` keeps the first-seen chain, a sound reading of the spec. Under either fix the committed test passes (for fix (a), adapt it to expect a construction error instead of a panic).
