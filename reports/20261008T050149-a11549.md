## Findings

### Off-by-requirement

#### Finding /1 — Engine accepts a block whose slot equals its parent's slot (spec requires strictly greater)

`20261008T050149-a11549/1` · severity **low** · confidence **high** · status **confirmed** (found by claude, confirmed by codex)

**Claim.** Block Header Validation step 5 requires `header.slot > fetch_header(header.parent_block).slot` — a strict inequality. The engine's `Branches::apply_header` (`consensus/cryptarchia-engine/src/lib.rs:244`) implements the check as `if parent_branch.slot > slot { return Err(InvalidSlot) }`, which rejects only a slot *smaller* than the parent's: a child claiming the same slot as its parent is accepted into the block tree and participates in fork choice. The engine's own test suite exercises this (`pruning_forks_when_receive_block` inserts a block at the tip's own slot), and the error message documents the weaker rule ("parent slot is greater than child slot", lib.rs:390). The rule matters beyond step 5: revision 1.2.5 of the spec derives the uncle-window implication `0 < sl_A - sl_U < W·f⁻¹` from its strictness.

**Location.** `consensus/cryptarchia-engine/src/lib.rs:244-246`

**Repro.** Test `consensus/cryptarchia-engine/tests/x20261008T050149-a11549-1.rs`: builds a tree with the LIB at slot 5, receives a child at slot 5, asserts `result.is_err()` per the spec sentence. Both passes ran it: `engine_rejects_block_whose_slot_equals_parent_slot ... FAILED` (exit 101) — `receive_block` accepted the equal-slot block.

```
cargo run --manifest-path bork-helpers/gmp-provision/Cargo.toml && cargo test --locked --config 'build.rustflags=["-L","native=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib","-C","link-arg=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib/libgmp.a"]' -p logos-blockchain-cryptarchia-engine --test x20261008T050149-a11549-1
```

**Evidence and scope.** Deterministic for any header with slot == parent slot. Mitigation inside the unit: the ledger's `update_epoch_state` (`ledger/src/cryptarchia/mod.rs:264-269`) rejects `slot <= self.slot`, and the chain service prepares the ledger update before calling the engine — so a full node rejects the block at the ledger stage, and the divergence is confined to the engine's block-tree acceptance API. Fix: change the guard to `>=` and update the error message; the engine unit test that inserts an equal-slot block needs adjusting.

#### Finding /4 — Genesis never counted in the epoch-zero block-density observation

`20261008T050149-a11549/4` · severity **low** · confidence **medium** · status **confirmed** (found by codex, confirmed by claude)

**Claim.** The Epoch State pseudocode defines the epoch-1 observation window as `0 <= sl < ⌊6k/f⌋` and counts the slots of all ancestors in that window, with no genesis exception. Genesis occupies slot 0, inside that window. `LedgerState::from_utxos` (`ledger/src/cryptarchia/mod.rs:753-759`) creates an empty `BlockDensity` for epoch 0 and never marks slot 0; because `update_epoch_state` rejects `slot <= self.slot`, slot 0 can never enter the set later either. The first total-stake inference therefore sees one fewer occupied slot than the pseudocode prescribes.

**Location.** `ledger/src/cryptarchia/mod.rs:753-759`, `ledger/src/cryptarchia/block_density.rs:17-20`

**Repro.** Test `ledger/tests/x20261008T050149-a11549-4.rs`: creates a genesis ledger, reads its serialized `occupied_slots`, asserts genesis contributed one slot, and requests the epoch-1 state from a large starting estimate to show the consequence. The merge pass ran it (the second pass could not — see environment note below): exit 101, printing `genesis observation: []; epoch 1 inferred stake: 1`, then `assertion left == right failed: epoch-zero density must count the genesis block at slot 0 / left: 0 / right: 1`. With zero observed density the first inference collapses the estimate to the minimum, where the spec-side count of one slot yields 1000 in the test's small configuration.

```
sh -c 'R=/tmp/bork-lbc-root; C=/w/cache/logos/blockchain/logos-blockchain-circuits-v0.5.7-linux-aarch64; rm -rf $R; mkdir -p $R; cp -rs $C/. $R/; mkdir -p $R/lib; cp bork-helpers/lbc-root/lib/libgmp.a $R/lib/; for c in pol poc poq signature; do mkdir -p $R/$c; for f in proving_key.zkey verification_key.json witness_generator.dat; do [ -e $R/$c/$f ] || echo bork-placeholder > $R/$c/$f; done; [ -e $R/$c/lib$c.a ] || printf "!<arch>\n" > $R/$c/lib$c.a; done' && cargo test --locked --config 'env.LBC_ROOT_DIR="/tmp/bork-lbc-root"' --config 'build.rustflags=["-L","native=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib","-C","link-arg=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib/libgmp.a"]' -p logos-blockchain-ledger --test x20261008T050149-a11549-4 -- --nocapture
```

**Evidence and scope.** Deterministic at initialization; affects the epoch-1 total-stake estimate and derived lottery constants, with later estimates inheriting the initial difference. At deployed constants the one-slot difference in a 194,400-slot window is small. Environment note: the cached circuits artifact has no `poq/` directory (and `poc/` lacks `witness_generator.dat`), so the ledger crate's `circuits-poq-sys` dependency fails at `include_bytes!` out of the box — the command above assembles a stub circuit root via the build script's documented `LBC_ROOT_DIR` override; the placeholder bytes are compile-time fodder only, never read at run time by this test. Fix: mark `Slot::genesis()` occupied when constructing the genesis ledger — or, if genesis (not being a lottery win) is intended to be excluded from density, state that exception explicitly in the pseudocode; the code and the pseudocode's letter currently disagree either way. That interpretation question is why confidence stays medium.

### Contradicts-spec

#### Finding /2 — Bootstrapping fork choice receives s = ⌊k/(4f)⌋ instead of the spec's s = 3⌊k/f⌋

`20261008T050149-a11549/2` · severity **medium** · confidence **medium** · status **confirmed** (found by claude, confirmed by codex)

**Claim.** The Notation table defines the slot security parameter `s = 3⌊k/f⌋`, and Chain Maintenance passes exactly this `s` to the fork choice: `fork_choice(c_loc, F_T', k, s)`. The Uncle Selection note reiterates the value (`W·f⁻¹ ≤ 0.6k/f = s/5`). The engine instead computes `Config::s_gen() = ⌊k/(4f)⌋` (`consensus/cryptarchia-engine/src/config.rs:107-113`) and passes it as the density-window parameter of `maxvalid_bg` during bootstrapping (`src/lib.rs:48-52`, window cutoff `lca.slot + s_gen` at lib.rs:106). At deployed constants (k=2160, f=1/30) that is 16,200 slots instead of 194,400 — a 12x narrower density-comparison window after a deep fork, changing which chain a bootstrapping node selects whenever fork density differs between the two windows.

**Location.** `consensus/cryptarchia-engine/src/config.rs:107-113`, `consensus/cryptarchia-engine/src/lib.rs:48-52`

**Repro.** Test `consensus/cryptarchia-engine/tests/x20261008T050149-a11549-2.rs`: instantiates `Config` with the spec constants and asserts `s_gen == 3 * base_period_length` per the Notation table. Both passes ran it: `assertion left == right failed ... left: 16200 / right: 194400` (exit 101).

```
cargo run --manifest-path bork-helpers/gmp-provision/Cargo.toml && cargo test --locked --config 'build.rustflags=["-L","native=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib","-C","link-arg=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib/libgmp.a"]' -p logos-blockchain-cryptarchia-engine --test x20261008T050149-a11549-2
```

**Evidence and scope.** Deterministic for every bootstrapping fork-choice evaluation that reaches the density rule (forks deeper than k); the Online rule (`maxvalid_mc`) does not use `s`. Attribution caveat (why confidence is medium despite the demonstrated test): the internals of `maxvalid_bg` are governed by the separate Fork Choice Rule LIP, which may define its own window — but the value `s` and the fact that Chain Maintenance passes it are normative in *this* document, so the divergence is traced here. If the fork-choice LIP deliberately uses k/(4f), the defect becomes spec-drift in this document's Notation table rather than a code bug; either way the two documents and the code currently disagree. Fix: reconcile with the Fork Choice Rule LIP — change `s_gen` to `3 * base_period_length()` or amend this document; the engine tests that back-compute `s_gen` need retuning if the code changes.

### Missing-requirement

#### Finding /3 — No "B ∈ T → ignore" guard: re-delivering a known interior block pollutes the tips set

`20261008T050149-a11549/3` · severity **low** · confidence **high** · status **confirmed** (found by claude, confirmed by codex)

**Claim.** Chain Maintenance begins `if B ∈ T ∨ ¬valid_header(B): return state` — a block already in the tree must leave the state unchanged. The engine's `receive_block`/`Branches::apply_header` (`consensus/cryptarchia-engine/src/lib.rs:232-268, 442-507`) performs no membership check: re-delivering an interior block executes `tips.remove_mut(&parent)` (a no-op) and `tips.insert_mut(header)`, adding a block that has children back into the tips set — violating the spec's tips definition `F_T = {b ∈ T : ∀c ∈ T, parent(c) ≠ b}`. The polluted entry is iterated by every subsequent fork-choice run, reported by `non_canonical_forks()`, and later treated as a prunable fork once the LIB passes it.

**Location.** `consensus/cryptarchia-engine/src/lib.rs:253-265`, `consensus/cryptarchia-engine/src/lib.rs:442-451`

**Repro.** Test `consensus/cryptarchia-engine/tests/x20261008T050149-a11549-3.rs`: builds g(0)–b1(1)–b2(2), re-delivers b1 (same id, parent, slot), asserts the tips set is still exactly {b2}. Both passes ran it: `assertion left == right failed ... left: [1, 2] / right: [2]` (exit 101).

```
cargo run --manifest-path bork-helpers/gmp-provision/Cargo.toml && cargo test --locked --config 'build.rustflags=["-L","native=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib","-C","link-arg=/w/work/20261008T050149-a11549/bork-helpers/lbc-root/lib/libgmp.a"]' -p logos-blockchain-cryptarchia-engine --test x20261008T050149-a11549-3
```

**Evidence and scope.** Deterministic on any duplicate delivery of a non-tip block to the engine API. A worse variant — same id with a *different* parent or slot — silently overwrites the stored Branch record (`branches.insert_mut`, lib.rs:256), retroactively changing the parent pointer and slot that descendants' chain walks traverse; under the specified body-committing block ID this is not an attacker scenario, but the API permits it. Fork-choice outcomes remain correct for the same-content duplicate (the stale tip is shorter than its descendants), and node-level callers in services/chain deduplicate via an AlreadyApplied guard before driving the engine — hence severity low; but the spec places the guard in this procedure, which the unit implements. Fix: return early (no state change, e.g. `Error::AlreadyKnown` or an Ok no-op) when `self.branches.contains_key(&header)`.
